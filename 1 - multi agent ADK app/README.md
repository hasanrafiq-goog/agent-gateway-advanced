# Stage 1 — Multi-Agent ADK 2.0 App with Skills & MCP Toolset

## 1. Goal of This Stage
Build a dynamic **Google ADK 2.0 (`google-adk >= 2.0.0`) Multi-Agent Application** scaffolded with `agents-cli` that combines:
1. **ADK 2.0 Task Delegation (`mode="task"`)**: A Coordinator agent delegating structured tasks to specialist sub-agents.
2. **ADK 2.0 Skills (`SkillToolset` + `SKILL.md`)**: Specialist agents that load markdown skills (`load_skill`) on demand.
3. **Dynamic MCP Tool Unlocking (`adk_additional_tools` + `McpToolset`)**: MCP tools from Stage 0 stay locked until the agent loads the relevant skill!

## 3. Important ADK 2.0 Learnings & Concepts

### A. Why We Scaffold with `agents-cli`
Running `agents-cli scaffold create order-assistant --agent adk --prototype` generates the full production wrapper around `app/agent.py`:
- **`app/agent.py`** — Pure Python agent definitions (`root_agent`, `order_tracker`, `refund_specialist`).
- **`app/fast_api_app.py`** — The production HTTP server required by Cloud Run and Vertex AI Agent Engine. It automatically wires up:
  - ADK REST & SSE streaming routes (`/run`, `/run_sse`) and the ADK Web UI (`web=True`).
  - **Built-in A2A (Agent-to-Agent) Protocol** (`attach_a2a_routes` at `/a2a/app` + `AgentCard`).
  - **Session & Artifact Services** (`InMemorySessionService` locally, `VertexAiSessionService` on Agent Engine).
  - **GCP Observability** (OpenTelemetry traces to Cloud Trace & logs to Cloud Logging).

### B. ADK 2.0 Task Mode (`mode="task"`) vs Graph `Workflow`
- **`mode="task"` on `Agent`** *(used here)*: Gives the Coordinator LLM dynamic control over which sub-agent to call and in what order. ADK 2.0 automatically injects a `finish_task` tool into each sub-agent to enforce a Pydantic `output_schema` (`OrderLookupOutput`, `RefundOutput`).
- **`Workflow(edges=[...])`**: ADK 2.0's deterministic graph engine where edges (not an LLM) dictate the exact path between nodes.

### C. How `SkillToolset` + `McpToolset` Work Together
In [`order-assistant/app/agent.py`](./order-assistant/app/agent.py), `McpToolset` is passed inside `SkillToolset(..., additional_tools=[McpToolset(...)])`:
- Before `load_skill` is called, the sub-agent **does not even connect to the MCP server** (`GET /sse` is not called) and cannot see `get_order` or `process_refund`.
- When the agent calls `load_skill({"skill_name": "refund-policy"})`, `SkillToolset` reads the `SKILL.md` frontmatter:
  ```yaml
  metadata:
    adk_additional_tools:
      - get_order
      - process_refund
  ```
- `SkillToolset` then connects to `MCP_SERVER_URL` and dynamically unlocks those MCP tools mid-turn!

## 6. Egress Gateway Certificate Lifecycle (`gateway_ca.crt`)

You might wonder: *How does Stage 1's code handle the Agent Gateway certificate if the gateway isn't created until Stage 3?*

[`order-assistant/app/agent.py`](./order-assistant/app/agent.py) is built to be **portable and lifecycle-aware**:
1. **Stage 1 (Local Development)**:
   - When running locally, no Agent Gateway exists yet.
   - `agent.py` checks `ca_cert_file = Path(__file__).parent / "gateway_ca.crt"`. If the file does not exist, it **gracefully skips injection** without raising an error. The local agent connects directly to the local or cloud MCP server.
2. **Stage 3 (Gateway Creation)**:
   - When Stage 3 creates the Egress Agent Gateway in Google Cloud, the gateway provisions a TLS root CA.
   - `3 - setup Agent Gateway and Registry/deploy.sh` automatically fetches this CA (`agentGatewayCard.rootCertificates`) and saves it to [`order-assistant/app/gateway_ca.crt`](./order-assistant/app/gateway_ca.crt).
3. **Stage 4 (Cloud Deployment)**:
   - `4 - deploy Agent on Agent Engine/deploy.sh` ensures `gateway_ca.crt` is in place, and `agents-cli deploy` packages it into the Vertex AI Reasoning Engine container image.
   - In production, `agent.py` reads `gateway_ca.crt` and appends it to `certifi`, `REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`, and `GRPC_DEFAULT_SSL_ROOTS_FILE_PATH`.
4. **Stage 5 (Policy Enforcement)**:
   - The Reasoning Engine can now perform outbound TLS-inspected MCP calls through the Agent Gateway without any SSL/TLS certificate errors, enabling Model Armor SDP masking and MCP tool denial.
